## 2. ServicesManager: Registrierung, Lookup, Lebensdauer

### 2.1 Register-Signatur (verifiziert, [J-SM])

Exakte Signatur laut Javadoc 26.3:

```text
<T> void register(@NotNull Class<T> service,
                  T provider,
                  @NotNull Plugin plugin,
                  @NotNull ServicePriority priority)
```

Parameter laut Javadoc: `service – service class`,
`provider – provider to register`, `plugin – plugin with the provider`,
`priority – priority of the provider`. Die Interface-Beschreibung sagt:

> „If multiple plugins register a service, then the service with the highest
> priority takes precedence.“

Für EndLock folgt daraus der Aufruf aus `onEnable`:
`getServicesManager().register(EndLockApi.class, provider, this, ServicePriority.Normal)`.

### 2.2 Unregister-Varianten (verifiziert, [J-SM])

- `void unregister(@NotNull Class<?> service, @NotNull Object provider)` –
  „Unregister a particular provider for a particular service.“
- `void unregister(@NotNull Object provider)` –
  „Unregister a particular provider.“
- `void unregisterAll(@NotNull Plugin plugin)` –
  „Unregister all the providers registered by a particular plugin.“

Ein explizites Unregister in `onDisable` ist zulässig, aber für die
Korrektheit nicht erforderlich (siehe 2.3).

### 2.3 Automatische Entfernung beim Plugin-Disable (verifiziert, [S-PPIM])

Der ausgeführte Disable-Pfad auf Paper ist
`PaperPluginManagerImpl.disablePlugin(plugin)` →
`PaperPluginInstanceManager.disablePlugin(plugin)` ([S-PPMI]; die
Bukkit-Legacy-Implementierung [S-SPM] delegiert anfangs per
`if (true) { ... paperPluginManager ... }` auf denselben Pfad). In
`PaperPluginInstanceManager.disablePlugin` steht die folgende,
implementierungsnah wiedergegebene Reihenfolge:

```java
this.server.getPluginManager().callEvent(new PluginDisableEvent(plugin));
...
this.server.getScheduler().cancelTasks(plugin);
this.server.getGlobalRegionScheduler().cancelTasks(plugin); // „Paper - Folia schedulers“
this.server.getAsyncScheduler().cancelTasks(plugin);
this.server.getServicesManager().unregisterAll(plugin);
HandlerList.unregisterAll(plugin);
...
```

**Festgestellt:** Ein über `register(..., this, priority)` registrierter
Service wird beim Disable vollständig automatisch entfernt – **nach** dem
Feuern von `PluginDisableEvent` und **vor** dem Abmelden der Event-Handler.

Damit erzwingt der Server bereits das ROADMAP-Abnahmekriterium „Der
API-Service ist nur verfügbar, solange EndLock aktiviert ist“. EndLock muss
selbst nur garantieren, dass der Provider erst nach dem Aufbau der internen
Zustandsobjekte registriert wird.

Implementierungsseite (verifiziert, [S-SSM]): `register` und die
`unregister`-Varianten arbeiten in `SimpleServicesManager` unter
`synchronized (providers)` und feuern `ServiceRegisterEvent` bzw.
`ServiceUnregisterEvent` pro betroffenem Provider.

Zur Übertragung auf Folia: Der Folia-Grundpatch „Region Threading Base“
([F-PPATCH]) enthält keine Änderungen an `unregisterAll` oder am
Plugin-Manager-Cleanup; es wird daher angenommen, dass Folia denselben Pfad
ausführt. Live verifiziert auf Folia wurde das nicht (Abschnitt 8).

### 2.4 Optionaler Lookup: `load` vs. `getRegistration` vs. `getRegistrations` (verifiziert, [J-SM] + [S-SSM])

| Methode | Verhalten laut Javadoc | Nutzen für EndLock-Verbraucher |
|---|---|---|
| `<T> T load(Class<T> service)` | „Queries for a provider. This may return **null** if no provider has been registered for a service. The **highest priority** provider is returned.“ | einfachster Weg für die Frage „EndLock installiert und aktiv?“ |
| `<T> RegisteredServiceProvider<T> getRegistration(Class<T> service)` | „Queries for a provider registration. This may return null if no provider has been registered for a service.“ | zusätzlich `getProvider()`/`getPlugin()`; ebenfalls höchster Rang |
| `<T> Collection<RegisteredServiceProvider<T>> getRegistrations(Class<T> service)` | „Get registrations of providers for a service. The returned list is unmodifiable.“ | nur nötig bei mehreren Anbietern; für EndLock nicht vorgesehen |
| `<T> boolean isProvidedFor(Class<T> service)` | „Do not check this first only to call `load(service)` later, as that would be a non-thread safe situation.“ | als Vorprüfung vor `load()` vermeiden; direkt `load()` bzw. `getRegistration()` verwenden |

Empfohlenes Verbraucher-Muster (entsprechend ROADMAP-§1 „bei fehlendem
Service ohne Fehler weiterlaufen“):

```java
static EndLockApi find() {
    RegisteredServiceProvider<EndLockApi> reg =
        Bukkit.getServicesManager().getRegistration(EndLockApi.class);
    return reg == null ? null : reg.getProvider();
}
```

`null` bedeutet: EndLock fehlt oder ist deaktiviert. Der Verbraucher soll
das Provider-Objekt **nicht** cachen, sondern bei Bedarf neu über `load()`
oder `getRegistration()` anfragen, weil der Service bei jedem
Disable/Enable-Zyklus entfernt und neu registriert wird (Abschnitt 2.3).

### 2.5 Fazit ServicesManager

Das Angebot über den ServicesManager ist auf Paper 26.3 machbar und
dokumentiert: Signatur [J-SM], threadsichere Implementierung [S-SSM],
Auto-Unregister beim Disable [S-PPIM]. Für EndLock bleibt bei der
Implementierung: Registrierung in `onEnable` nach dem Aufbau der
Zustandsobjekte, Provider-Klasse bleibt intern und delegiert nur
`isLocked()` / `getLockReason()`. Der Vertrag von `getLockReason()`
(Plain Text ohne MiniMessage-Tags? leeres Verhalten ohne Grund?) ist
Implementierungspunkt und nicht hier verifiziert (Risiko R4).

## 3. Eigene Events auf Paper 26.3

### 3.1 Anforderungen an eine Event-Klasse (verifiziert, [J-EV] / [J-HL] / [S-PEM])

Zitat [J-EV]:

> „All events require a static method named `getHandlerList()` which returns
> the same `HandlerList` as `getHandlers()`.“

Aus dem tatsächlichen Registrierungspfad ([S-PEM], `registerEvents` →
`getEventListeners` → `getRegistrationClass`):

- Die statische Methode wird per `getDeclaredMethod("getHandlerList")`
  gesucht und über `method.invoke(null)` aufgerufen; sie **muss** `static` sein.
- Fehlt sie, wirft der Code
  `IllegalPluginAccessException("Unable to find handler list for event <class> . Static getHandlerList method required!")`.
  Die Klassenhierarchie wird nach oben durchsucht (bis zur obersten
  Nicht-`Event`-Superklasse); `Event` selbst definiert keine
  `getHandlerList`-Methode.

Standard-Schablone für `EndLockStateChangeEvent`:

```java
public final class EndLockStateChangeEvent extends Event {
    private static final HandlerList HANDLER_LIST = new HandlerList();

    public EndLockStateChangeEvent(/* prev, next, action, actor ... */) {
        super(); // Event() -> synchrones Event, laut [J-EV]
        // Felder setzen ...
    }

    @Override
    public HandlerList getHandlers() { return HANDLER_LIST; }

    public static HandlerList getHandlerList() { return HANDLER_LIST; }
}
```

Zum Abbrechen: [J-EV] beschreibt `callEvent()` als „Calls the event and
tests if cancelled“. Ohne `Cancellable`-Interface kann das Event nicht
abgebrochen werden. Das erfüllt die Vorgabe „nicht abbrechbar“ (ROADMAP-§1).

### 3.2 Thread-Vertrag: `callEvent()` vom Nicht-Main-Thread (verifiziert, [S-PEM])

Der ausgeführte Dispatch auf Paper ist
`PaperPluginManagerImpl.callEvent(event)` → `PaperEventManager.callEvent(event)`
([S-PPMI], [S-PEM]). Die tatsächlichen Thread-Checks in [S-PEM] lauten:

```java
if (event.isAsynchronous() && this.server.isPrimaryThread()) {
    throw new IllegalStateException(event.getEventName() + " may only be triggered asynchronously.");
} else if (!event.isAsynchronous() && !this.server.isPrimaryThread() && !this.server.isStopping()) {
    throw new IllegalStateException(event.getEventName() + " may only be triggered synchronously.");
}
```

Einschätzung für EndLock:

1. `EndLockStateChangeEvent` wird als **synchrones Event** definiert
   (Default-Konstruktor `Event()`, laut [J-EV] „assumes the event is
   synchronous“).
2. Dispatch eines synchronen Events von einem Thread, auf dem
   `server.isPrimaryThread()` false liefert, wirft eine
   `IllegalStateException`
   (`"<Eventname> may only be triggered synchronously."`), außer während des
   Shutdowns (`this.server.isStopping()`).
3. Die historische Bukkit-Meldung „asynchronous <event> broadcast“ kommt im
   aktuellen Paper-Servercode nicht mehr vor. Die älteren Meldungen in der
   Legacy-Implementierung [S-SPM]
   („... cannot be triggered synchronously from another thread.“) sind im
   Paper-Pfad deaktiviert, weil `SimplePluginManager` fast jede Methode
   sofort an `paperPluginManager` delegiert.
4. Konsequenz: Das Event darf **nie** aus dem AsyncScheduler oder aus
   eigenen Plugin-Worker-Threads gefeuert werden. Nach Abschnitt 5 läuft
   `changeLockState` in der aktuellen Codebasis jedoch nie asynchron; der
   vorhandene Pfad erfüllt diese Anforderung bereits.

### 3.3 Listener-Ausführung zum Dispatch-Zeitpunkt (verifiziert, [S-PEM])

Listener werden synchron im aufrufenden Thread von `callEvent()` ausgeführt.
Fehler in Listenern werden abgefangen, geloggt und (Paper-spezifisch) in
`ServerExceptionEvent` verpackt; ein fehlerhafter Listener bricht nicht die
Ausführung der übrigen Listener ab. Listener von deaktivierten Plugins
(!`isEnabled()`) werden im Dispatch übersprungen:

```java
for (RegisteredListener registration : listeners) {
    if (!registration.getPlugin().isEnabled()) {
        continue;
    }
    ...
}
```

API-Bedeutung: Ein Verbraucher, der zum Dispatch-Zeitpunkt deaktiviert ist,
erhält zu diesem Zeitpunkt kein Event; nach einem Re-Enable erhält er bei
weiteren Zustandswechseln wieder eines.

## 4. Folia: Was die Region-Threading-Plattform für die API bedeutet

Alle Aussagen dieses Abschnitts basieren auf [F-README], [D-FOLIA], [D-FAQ],
[F-PPATCH], [F-MCPATCH] und [J-FSV], Stand Branch `ver/26.3.x`.

### 4.1 Kein globaler „main thread“ (verifiziert, [F-README], [D-FOLIA])

Wörtzitate [F-README]:

> „There is no main thread anymore, as each region effectively has its own
> ‘main thread’ that executes the entire tick loop.“

> „The async modifier for events is deprecated - all events fired from
> regions or the global region are considered synchronous, even though
> there is no main thread anymore.“

Zitat [D-FOLIA] zur „Global Region“:

> „The global region is a single scheduled task that is always scheduled to
> run at 20TPS that is responsible for maintaining data that is not tied to
> any specific region: game rules, global game time, daylight time, console
> command handling, world border, weather, and others.“

Konsequenz für Custom-Sync-Events auf Folia: Der Thread-Check aus Abschnitt 3.2
hängt an `server.isPrimaryThread()`. In der Paper-Serverquelle ist die
Implementierung ([S-CS], Kommenteintrag „Paper - rewrite chunk system“):

```java
@Override
public boolean isPrimaryThread() {
    return ca.spottedleaf.moonrise.common.util.TickThread.isTickThread();
}
```

Auf Folia sind die Regionen-Tick-Threads und der Global-Region-Tick-Thread
`TickThread`-Instanzen. Folia definiert in [F-MCPATCH]
`TickThreadRunner extends TickThread` und führt die Regionen über den
`TickRegionScheduler` aus; `RegionizedServer.isGlobalTickThread()` identifiziert
den Global-Region-Thread ([F-MCPATCH]). Ergebnis:

| Ausführungskontext auf Folia | Sync-Event (`EndLockStateChangeEvent`) zulässig? |
|---|---|
| Regionen-Tick-Thread | ja |
| Global-Region-Tick-Thread (u. a. Konsole) | ja |
| AsyncScheduler / eigener Plugin-Worker-Thread | **nein** (IllegalStateException, [S-PEM]) |
| Shutdown-Thread | Sonderregel über `isStopping()` in [S-PEM]; **nicht live verifiziert** |

Das Folia-Javadoc ([J-FSV]) dokumentiert die zugehörigen Plattform-APIs:
`isPrimaryThread()`, `isGlobalTickThread()`
(„Returns whether the current thread is ticking the global region.“) und die
Familie `isOwnedByCurrentRegion(...)` (Region-Besitz von Positionen und
Entities).

Auch hier gilt der Vorbehalt ohne Live-Lauf: „nicht verifiziert auf Folia
Build 5 ALPHA“, auch wenn [F-README] als Dokumentation dafür spricht
(siehe 4.4).

### 4.2 Command-Dispatch-Kontext auf Folia (verifiziert, [F-README] + [F-PPATCH])

Zitat [F-README]:

> „1. Commands for entities/players are called on the region which owns the
> entity/player. Console commands are executed on the global region.“

Im Servercode ([F-PPATCH], `CraftServer.dispatchCommand`) steht:

```java
// Folia - region threading
if ((rawSender instanceof Entity entity)) {
    ca.spottedleaf.moonrise.common.util.TickThread.ensureTickThread(
        ((org.bukkit.craftbukkit.entity.CraftEntity) entity).getHandle(),
        "Dispatching command async");
} else if (rawSender instanceof ConsoleCommandSender
        || ...
        || rawSender instanceof FeedbackForwardingSender) {
    io.papermc.paper.threadedregions.RegionizedServer.ensureGlobalTickThread(
        "Dispatching command async");
}
```

Für EndLock heißt das: ein `/endlock lock` durch einen Spieler läuft auf
Folia auf dem Tick-Thread der Region, die diesen Spieler besitzt; ein
Konsolenaufruf läuft auf dem Global-Region-Thread. Beides sind synchrone
Tick-Kontexte (4.1) und damit zulässige Orte für `changeLockState` und das
Event.

### 4.3 GlobalRegionScheduler und Listener-Regeln (verifiziert, [J-GRS], [R-SCHED])

Zitat [J-GRS]:

> „The global region task scheduler may be used to schedule tasks that will
> execute on the global region. The global region is responsible for
> maintaining world day time, world game time, weather cycle, sleep night
> skipping, executing commands for console, and other misc. tasks that do
> not belong to any specific region.“

EndLock nutzt bereits exakt diese Scheduler-API ([R-SCHED]):

- `ScheduleManager.scheduleDueCheck()` ruft
  `plugin.getPaperScheduler().runGlobalLater(...)` auf; das ist intern
  `getServer().getGlobalRegionScheduler().runDelayed(plugin, ...)`
  ([R-SCHED], `PaperScheduler`).
- Der fällige Zeitplan-Aufruf `executeDueAction()` und damit
  `plugin.changeLockState(targetLocked, "System", "SCHEDULED_...")`
  ([R-SCHED] Zeile 380) läuft dadurch auf dem **Global-Region-Thread (Folia)**
  bzw. auf dem **Main-Thread (Paper)**.
- Der Countdown („countdown-lock/unlock-notification“) läuft analog über
  `runGlobalRepeating` → `runAtFixedRate(...)` ([R-SCHED]).

Folia-Regeln für Listener, die Welt- oder Spielerzustand ändern wollen
(Zitat [F-README]):

> „Folia compatible plugins need to take advantage of API like the
> RegionScheduler and the EntityScheduler to ensure their code is running on
> the correct thread context.“

[D-FOLIA] führt die Hilfs-Utilities `EntityScheduler`,
`RegionizedTaskQueue`, „global region task queue“ und `RegionizedData`
auf. Für die EndLock-API-Dokumentation folgt deshalb: das Event übermittelt
nur Payload (alt/neu/Aktion/Akteur) und **verpflichtet** Listener, jede
Welt- oder Spieleränderung selbst über Region-/Entity-/Global-Scheduler zu
schedulen. Das entspricht der Abgrenzung aus ROADMAP-§1: „Listener dürfen
daraus keine implizite Berechtigung ableiten, beliebige Welt- oder
Spielerdaten synchron zu ändern.“

### 4.4 Folia Build 5 ALPHA (Repository-Konfiguration [R-BUILD]; Einschätzung aus [F-README])

EndLock pinnt lokal Folia 26.3 Build 5 (ALPHA) für Kompatibilitätstests via
`runPaper.folia.registerTask { build(5) }` [R-BUILD, Zeilen 66–70]. Die
generelle Folia-Einschätzung aus demselben README:

> „Currently, there is a lot of API that relies on the main thread. I expect
> basically zero plugins that are compatible with Paper to be compatible
> with Folia.“

> „So, have your expectations for compatibility at 0.“

„Current broken API“ ([F-README]):

- „Most API that interacts with portals / respawning players / some player
  login API is broken.“
- „ALL scoreboard API is considered broken (this is global state ...).“
- „World loading/unloading“
- „Entity#teleport. This will NEVER UNDER ANY CIRCUMSTANCE come back, use
  teleportAsync.“
- „Could be more“

„Planned API changes“ ([F-README]):

> „Super aggressive thread checks across the board. This is absolutely
> required to prevent plugin devs from shipping code that may randomly
> break random parts of the server in entirely undiagnosable manners.“

Bewertung für `EndLockStateChangeEvent`:

- Das Event selbst berührt keinen der als „broken“ gelisteten Pfade
  (keine Portal-/Respawn-/Login-Mechanik, keine Scoreboards, keine
  Welt-Ladung, keine `Entity#teleport`-Aufrufe im eigenen Pfad).
- Der eigene Dispatch ist „synchroner Tick-Thread → callEvent“ und ist der
  Mechanismus, den Folia laut README als synchron behandelt (4.1).
  Eine zusätzliche, event-spezifische Thread-Prüfung auf Folia Build 5
  ALPHA ist durch die Lektüre nicht festgestellt, aber **nicht live
  geprüft**.
- Für die API-Dokumentation: der Vertrag sollte von „synchroner
  Tick-Kontext; Listener mutieren Welt/Spieler nur über Scheduler“ getragen
  werden und nicht von „Thread X garantiert“. Dann bleibt das Design auch
  bei zukünftigen, engeren Thread-Checks stabil.

### 4.5 Folia-FAQ (verifiziert, [D-FAQ])

[D-FAQ] listet eine Reihe von Vanilla-Commands, die Folia deaktiviert
(u. a. Bossbar, Clone, Datapack, Debug, Function, Reload, Ride, Schedule,
Scoreboard, Team, Tick, Trigger). Plugin-Commands (wie `/endlock`, via
Paper lifecycle registriert, [R-CMD]) sind in dieser Liste nicht aufgeführt.
Eine ausdrückliche Aussage „Plugin-Commands funktionieren auf Folia“ gibt
es in der Doku nicht; die praktische Kompatibilität bleibt Prototyp-Aufgabe.

| 2 | `/endlock undo` → `EndLockCommand.undo` → `UndoCommand.execute` → `plugin.undoLastAction(actor, actorUuid)` → `changeLockState(restored, actor, "UNDO", actorUuid)` | [R-CMD] Zeilen 363/40; [R-LOCK] Zeilen 236–246 | main thread | wie (1) |
| 3 | `ScheduleManager.executeDueAction()` → `plugin.changeLockState(targetLocked, "System", "SCHEDULED_" + ...)`. Dessen Aufrufer läuft innerhalb der Global-Region-Scheduler-Task: `checkTask = plugin.getPaperScheduler().runGlobalLater(...)` (Zeilen 371–374), was intern `getServer().getGlobalRegionScheduler().runDelayed(...)` ist ([R-SCHED] `PaperScheduler`). | [R-SCHED] Zeile 380 | main thread | **Global-Region-Thread** |
| – | Countdown-Notifications (`runGlobalRepeating`) | [R-SCHED] Zeilen 400–418; kein `changeLockState`-Pfad | main thread | Global-Region-Thread |
| – | `/endlock lockat`/`unlockat`, `handleLockIn`/`handleUnlockIn` | schreiben nur eine ausstehende Aktion in `ScheduleManager`; führen kein sofortiges `changeLockState` aus | – | – |

Festgestellte Pfad-Eigenschaften:

1. **Kein Async-Pfad.** Es gibt im aktuellen Codestand keinen
   `changeLockState`-Aufruf aus `runAsync`-Tasks oder aus eigenen Threads;
   alle Wege laufen über Command-Executors oder Global-Region-Scheduler-Tasks.
2. **Guard „nur bei Änderung“:** `changeLockState` gibt `false` zurück, wenn
   `locked == newLocked` ([R-LOCK] Zeilen 205–207). In diesem Fall findet
   kein State-Change statt und es wird kein Event ausgelöst. Das deckt die
   ROADMAP-Bedingung ab: „nicht ausgelöst, wenn der gewünschte Zustand
   bereits aktiv ist oder eine Änderung fehlschlägt“.
3. **Persistiertes Zustands-Rückladen in `onEnable`:** [R-LOCK] (Zeilen
   146–150) ruft `evacuation.schedule()`, aber **kein** `changeLockState`;
   es gibt damit kein Event beim Serverstart für einen bereits gesetzten
   Zustand. Das ist konsistent mit dem Event-Vertrag „Änderungsereignis“.
4. **`undoLastAction`** feuert das Event (via `changeLockState`) mit
   `action="UNDO"`, aber nur, wenn die Zustandsänderung tatsächlich
   stattfand ([R-LOCK] Zeilen 236–246: `if (changed) {
       historyCommand.clearLastPreviousState(); }`).

## 6. API-Design-Konsequenzen (Entwurfsstand, nicht implementiert)

### 6.1 Service-Angebot

Interface-Entwurf (aus ROADMAP-§1, unverändert übernommen):

```java
public interface EndLockApi {
    boolean isLocked();
    String getLockReason();
}
```

Registrierung:

```java
// in onEnable, NACH dem Aufbau der internen Zustandsobjekte:
// (provider ist eine interne, nicht-öffentliche Implementierungsklasse)
getServer().getServicesManager().register(
    EndLockApi.class, provider, this, ServicePriority.Normal);
```

Konsequenzen:

- Das Auto-Unregister beim Disable ist serverseitig garantiert [S-PPIM];
  ein explizites `unregister(...)` in `onDisable` ist optional, aber
  zulässig als defensive Absicherung.
- Der `getLockReason()`-Kontrakt (Plain Text vs. MiniMessage, leeres
  Verhalten ohne gesetzten Grund) muss vor der Implementierung festgelegt
  werden; es gibt hierfür **noch keine verifizierte Quellen-Aussage** (R4).
- Konfigurations- und Implementierungsdaten werden nicht freigegeben
  (ROADMAP-§1: „Es werden keine Config-Objekte, internen Manager oder
  veränderbaren Sammlungen veröffentlicht.“).

### 6.2 Event-Entwurf (nur bei erfolgreicher Änderung, nicht abbrechbar)

Feldvorschlag (aus ROADMAP-§1):

- `previousLocked` / `newLocked` (`boolean`),
- `action` (`String`: `"LOCK"`, `"UNLOCK"`, `"UNDO"`, `"SCHEDULED_LOCK"`,
  `"SCHEDULED_UNLOCK"`; als stabile String-Enum im API-Paket dokumentiert),
- `actorName` (`@Nullable String`) und `actorUuid` (`@Nullable UUID`);
  gesetzt durch den Command-Akteur ([R-CMD] `actor.name()` /
  `actor.uuid()`); beim Zeitplan-Aktor „System“ derzeit `null`
  ([R-SCHED] Zeile 380).

Regeln aus dieser Recherche:

1. **Nicht abbrechbar** (kein `Cancellable`); das Event meldet eine bereits
   abgeschlossene, erfolgreiche Änderung (ROADMAP-§1). Der
   genaue Feuerrpunkt innerhalb `changeLockState` ist eine
   Implementierungsaufgabe; der Fall „Persistenz-/Broadcast-Fehler“ ist
   im Prototyp zu prüfen (R6).
2. **Nur bei erfolgreicher Änderung:** siehe 5.2.
3. **Thread-Kontext** (4.1, 4.2, 5): Paper main thread / Folia
   Spielerregion bzw. Global-Region-Thread, **nie** ein
   AsyncScheduler-Thread (sonst `IllegalStateException`, [S-PEM]).
4. **Listener-Regeln** (4.3): Payload nur lesen; Welt- und Spieler-Mutationen
   selbst schedulen (RegionScheduler/EntityScheduler). Der direkte
   Zustandszugriff im Handler ist auf beiden Plattformen unzulässig.
5. **Folia:** Regionen- und Global-Region-Threads sind für Sync-Events
   zulässige Dispatch-Kontexte; `isPrimaryThread()` ist als allgemeines
   Tick-Thread-Kriterium zu lesen ([S-CS]); `isGlobalTickThread()`
   ([J-FSV]) identifiziert die Global Region.

### 6.3 Verbraucher-Muster (gemäß ROADMAP-§1)

```java
EndLockApi api = find(); // null, wenn EndLock fehlt oder deaktiviert ist
if (api != null) {
    // Status-Abfrage im eigenen Lebenszyklus
}

@EventHandler
public void onChange(EndLockStateChangeEvent e) {
    // Payload lesen (prev/next/action/actor);
    // keine direkten Welt-/Spieler-Mutationen, sonst Scheduler nutzen.
}
```

Auf Folia ist kein besonderes „global event handler“-Muster erforderlich:
Das Sync-Event läuft im Dispatcher-Thread (Kontext von `changeLockState`),
und die übliche Bukkit-`@EventHandler`-Registrierung bleibt gültig
([S-PEM] `registerEvents`). Wichtig ist die Regel „keine Mutation von
Welt/Spieler aus dem Handler“, weil der Handler-Kontext plattformabhängig
ein Spielerregion- oder Global-Region-Thread ist.

## 8. Offene Risiken

1. **R1 – Folia Build 5 ALPHA ist laufzeitungetestet.** Die Festlegung „Event
   läuft auf synchronem Tick-Kontext“ beruht auf Quelltextlektüre, nicht auf
   einem Live-Aufruf. ROADMAP-§3 verlangt ohnehin echte Folia-Tests, bevor
   die Kompatibilitätsbehauptung erweitert wird. Für die API gilt: Prototyp
   (Abschnitt 9) auf Paper und Folia durchführen, das Event erst danach
   anbieten. Weiterhin gilt laut ROADMAP-§2: „Wenn Service-Lebenszyklus oder
   Event-Threading nicht sauber mit Paper und Folia vereinbar sind, sollte
   der Releaseumfang zunächst auf eine dokumentierte Statusabfrage
   begrenzt werden.“
2. **R2 – Javadoc-Build ist nicht das kompilierte Build.** Die Javadoc-Seiten
   zeigen `26.3.build.230-stable`, das Projekt kompiliert gegen
   `26.3.build.209-stable`. Für die geprüften Klassen ist kein Abweichen
   festgestellt, aber es ist nicht Diff-geprüft. `gradlew compileJava` beim
   Prototyp ist der finale Beweis (AGENTS-§3-Verifikationsprotokoll).
3. **R3 – Zukünftige Folia-Thread-Checks.** „Super aggressive thread
   checks across the board“ ist offiziell als Planung dokumentiert
   [F-README]. Der API-Vertrag sollte deshalb nur „synchroner
   Tick-Kontext; Listener mutieren Welt/Spieler nur über Scheduler“
   zusichern und nicht „Thread X garantiert“.
4. **R4 – `getLockReason()`-Kontrakt offen.** Plain Text ohne
   MiniMessage-Tags wäre konsistent mit den PlaceholderAPI-Regeln aus
   AGENTS-§5, aber das ist hier nicht verifiziert. Vor dem Prototyp
   festlegen (Verhalten ohne gesetzten Grund, leerer Zustand, Unicode).
5. **R5 – Reload-/Re-Enable-Zyklus.** Da der Service beim Disable
   automatisch entfernt wird und die Event-Handler des Verbrauchers
   ebenfalls ([S-PPIM] `HandlerList.unregisterAll(plugin)`), müssen
   Verbraucher nach einem Re-Enable von EndLock ihre Listener neu
   registrieren und den Service neu anfragen. Szenarien „EndLock reload,
   Verbraucher bleibt“ müssen im Prototyp dokumentiert werden, damit keine
   veralteten Provider-Referenzen entstehen.
6. **R6 – Persistenz-/Broadcast-Fehlverhalten.** „Nur bei erfolgreicher
   Änderung“ ist für den Normalpfad klar (Guard in [R-LOCK]), aber das
   Verhalten bei Config-Save- oder Broadcast-Fehlern innerhalb
   `changeLockState` ist nicht verifiziert und muss im Prototyp besprochen
   werden (z. B. Event vor/nach Persistenz-Zweig, Fehlerlog-Verhalten).

  1. `/endlock lock` + `/endlock unlock` via Konsole: genau ein Event pro
     Zustandswechsel.
  2. `/endlock lock` + `/endlock unlock` durch einen Spieler: auf Folia
     prüfen, dass der Event-Dispatch auf dem Spieler-Region-Thread

  4. `/endlock undo` nach einer Änderung: `action="UNDO"`, genau ein Event.
  5. Direktes Wiederholen desselben Zielzustands: kein Event (Guard in

- Erst bei erfolgreichem Prototyp: Vertrag stabilisieren, Tests, Beispiel
  und Kompatibilitätsregeln festlegen (ROADMAP-§2, Schritt 4); danach erst
  Implementierung mit `gradlew build` grün.

## 10. Zusammenfassung

- **Service über den ServicesManager** ist auf Paper 26.3 machbar und
  dokumentiert. Das Auto-Unregister beim Plugin-Disable ist quellcode-
  verifiziert [S-PPIM]; das Folia-Verhalten ist quellcode-plausibel
  identisch, aber nicht live geprüft. Verbraucher dürfen den Provider nicht
  cachen und fragen dynamisch per `load()` / `getRegistration()` nach.
- **Ein eigenes, nicht abbrechbares Sync-Event** ist auf Paper 26.3
  realisierbar ([J-EV], [J-HL]). Der Thread-Vertrag ist strikt: Dispatch vom
  falschen Thread wirft eine `IllegalStateException` ([S-PEM]). Der
  EndLock-Bestandscode nutzt `changeLockState` nur auf synchronen
  Tick-Kontexten (Command, Undo, Zeitplan), damit ist der Event-Dispatch
  zulässig.
- **Folia:** Regionen- und Global-Region-Threads gelten laut README als
  „synchron“ für Events ([F-README]); der Command-Dispatch-Ort ist
  dokumentiert ([F-PPATCH]). Der API-Vertrag sollte nicht auf ein konkretes
  Thread-Ablauf-Muster fixieren, sondern auf „synchroner Tick-Kontext und
  Listener-Scheduler-Regeln“, damit er auch bei künftigen Folia-Änderungen
  stabil bleibt.

Die Quellenrecherche bestätigt damit den Weg der ROADMAP:
Der Prototyp aus ROADMAP-§2 kann gestartet werden, sobald der
`getLockReason()`-Kontrakt (Risiko R4) und der Prototyp-Ablauf (Abschnitt 9)
festgelegt sind. Bis dahin bleibt der Vorschlagscharakter der 3.1-API
laut ROADMAP unverändert.
