# EndLock 3.1 API – Feasibility and Verification Notes

> **Status:** Research record for the implemented read-only API. The original
> proposal is no longer the current status: `EndLockApi`,
> `EndLockStateChangeEvent`, and a standalone consumer example are implemented.
> This document records the design constraints, source checks, and remaining
> verification limits; it does not claim that every player/world path has
> been live-tested.
>
> Target: Java 25, Paper API 26.3 Build 209, Paper 26.3, and Folia 26.3 Build 5
> ALPHA. Verified alongside the
> [API contract](3.1-api-contract.md) and
> [prototype report](3.1-prototype-verification.md).

## 1. Goal and result

The API lets other plugins query EndLock's current runtime state and observe
real state transitions without reading EndLock's config or implementation
classes. The first release intentionally exposes only:

- `EndLockApi#isLocked()` and `EndLockApi#getLockReason()`, via Paper's
  `ServicesManager`.
- A synchronous, non-cancellable `EndLockStateChangeEvent`.

The API is read-only. Lock changes continue through EndLock's existing
commands and state-transition logic, preserving history, persistence,
broadcasts, schedules, grace periods, and evacuation behavior.

## 2. Paper API checks

The following Paper 26.3 APIs were checked against their Javadoc and
implementation:

| API | Finding | Design consequence |
|---|---|---|
| `ServicesManager#register(Class<T>, T, Plugin, ServicePriority)` | Registers a provider with explicit priority. A missing lookup may return `null`. Providers are associated with the owning plugin. | Register the read-only provider at `Normal` after state initialization; consumers look it up dynamically and tolerate absence. |
| `ServicesManager#getRegistration(...)` | Supports retrieving the current provider registration. | Do not cache the provider across EndLock disable. |
| `Event` and `HandlerList` | Custom events use the standard synchronous event pattern and a static handler list. | `EndLockStateChangeEvent` is a normal synchronous Bukkit/Paper event and is not cancellable. |
| Plugin disable path | Paper unregisters services owned by the disabled plugin and unregisters its event handlers. | The provider is removed with EndLock's lifecycle. |
| `GlobalRegionScheduler` | Provides tasks for global state and work not owned by one specific region. | EndLock's scheduled state changes and wrapped command executors use the global tick context. |

## 3. Folia and dispatch context

Folia has region tick threads rather than one universal main thread. Its
documentation describes a global region for state not owned by a particular
region, including console command handling. Paper's synchronous event
dispatcher checks that an event is fired from a valid synchronous tick
context; an asynchronous worker is not valid.

Relevant references:

- [Folia 26.3.x README](https://github.com/PaperMC/Folia/blob/ver/26.3.x/README.md)
- [Folia overview](https://docs.papermc.io/folia/reference/overview/)
- [Folia FAQ](https://docs.papermc.io/folia/faq/)
- [Paper 26.3 `GlobalRegionScheduler`](https://jd.papermc.io/paper/26.3/io/papermc/paper/threadedregions/scheduler/GlobalRegionScheduler.html)

EndLock-specific code inspection found:

- Command wrappers route all EndLock executors, including player-originated
  executors, through `PaperScheduler.executeGlobal`.
- Scheduled lock/unlock actions use `PaperScheduler`'s global scheduling
  methods.
- Consequently, the state transition and event dispatch occur on Paper's main
  tick thread or Folia's global-region tick thread, not on the player's region.
- A consumer listener must schedule its own world/entity changes on the
  correct global, region, or entity scheduler. Event delivery does not grant
  ownership of arbitrary world or player state.

The consumer prototype confirmed the global synchronous dispatch context for
console and scheduled paths on both test servers. Player command and world
interaction paths on Folia remain unverified with a live player.

## 4. Lifecycle, optional dependencies, and class loading

The service is registered during EndLock enable after the runtime state and
reason provider are available. The service is registered under EndLock's
plugin ownership and is removed when EndLock is disabled.

For consumers:

- Use `softdepend: [EndLock]` when the integration is optional.
- Look up the service when needed and treat a missing registration as normal.
- Do not cache the provider across a disable cycle.
- Because API classes are supplied by EndLock and are absent without it,
  isolate API references in a separate integration class if the consumer must
  also load without EndLock.
- Hot-enabling or hot-reloading EndLock while the consumer remains enabled is
  not supported. Restart the server after changing EndLock.

The standalone consumer demonstrates the isolated class-loading pattern.
An independent runtime smoke test with EndLock absent remains useful and has
not yet been run.

## 5. Contract decisions

### Plain-text lock reason

The API returns effective display text, not MiniMessage markup. The provider
strips recognized MiniMessage tags and valid legacy `§` formatting codes.
Ordinary text such as `Portal <The End>` is preserved. The existing
`LockReasonManager` fallback of `"Maintenance"` remains in effect when the
default reason is missing; an explicitly empty value remains empty. The result
is never `null`.

### State-change event

The event reports a runtime transition that has already occurred. The runtime
state is updated before persistence and other side effects. The event is
dispatched even if a later side effect throws. If both a side effect and event
dispatch fail, the original side-effect exception is rethrown and the event
exception is attached as suppressed.

This semantics distinguishes “runtime state changed” from “all side effects
succeeded.” The partial-failure path is implemented but has not been tested
with an injected failure.

### Scope of the action value

The current action values are `LOCK`, `UNLOCK`, `UNDO`, `SCHEDULED_LOCK`, and
`SCHEDULED_UNLOCK`. The set is intentionally open so compatible releases can
add actions. Consumers should not reject unknown strings.

## 6. Distribution decision

For 3.1, the API ships inside the EndLock release JAR and consumers use that
JAR as a `compileOnly` dependency. The API is not separately published to
Maven Central or JitPack; consumers must not shade the API classes. This
avoids adding a new release/publishing mechanism before a concrete need is
established.

## 8. Remaining work

Before expanding compatibility claims, run Folia with real players through
player-issued lock commands, portal/travel blocking, respawn, evacuation,
join notification, and grace-period scenarios. Also run the consumer without
EndLock installed. Keep documentation limited to the paths actually tested.
