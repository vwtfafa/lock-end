# EndLock 3.1 API – Live Prototype Verification

> **Status:** Live verification of the service and console/scheduled paths on
> Paper and Folia. Player-driven paths have not been tested with a live player
> and remain explicitly unverified.

## 1. Prototype

The consumer plugin in [`examples/api-consumer`](../examples/api-consumer)
(`EndLockApiConsumer` 0.1.0) is built using the documented distribution model:
Paper API 26.3 Build 209 plus the EndLock release JAR as `compileOnly`, with
`softdepend: [EndLock]`.

The consumer:

- Loads API-dependent code only when EndLock is enabled. API type references
  are isolated in `EndLockApiIntegration`.
- Looks up the service on demand; it does not cache the provider.
- Registers an event listener only when EndLock is available at startup.
- Runs a 60-second status tick through `GlobalRegionScheduler`.
- Runs the console sequence `lock` → `lock` (guard) → `unlock` → `undo` →
  `status`, then shuts down after five minutes.
- Does not access worlds or players in the event handler.

Hot-enabling or hot-reloading EndLock while the consumer remains enabled is
not supported. Restart the server after changing EndLock.

## 2. Environments and results

Both servers were launched with the repository's Gradle tasks. Runtime files
are under the gitignored `run/` and `run/folia/` directories.

| Platform | Server build | Run | Result |
|---|---|---|---|
| Paper 26.3 | Build 235 stable (latest at test time) | Scheduled run: 2026-10-31; console run: 2026-11-01 | All tested scenarios passed |
| Folia 26.3 | Build 5 ALPHA | Scheduled run: 2026-10-31; console run: 2026-11-01 | All tested scenarios passed |

The project itself compiles against Paper API 26.3 Build 209. The exercised
API surface behaved identically on the tested Paper server build.

| Scenario | Expected behavior | Result |
|---|---|---|
| Startup service lookup | `locked=false`; effective reason is `Maintenance` | Passed on both |
| 60-second status tick | Fresh lookup reflects current state | Passed on both |
| Console `endlock lock` | Exactly one `LOCK` event with correct actor and state | Passed on both |
| Repeated `endlock lock` | No event when already locked | Passed on both |
| Console `endlock unlock` | Exactly one `UNLOCK` event; previous/new values correct | Passed on both |
| Console `endlock undo` | Exactly one `UNDO` event | Passed on both |
| Console `endlock status` | Read-only status command succeeds | Passed on both |
| Scheduled lock | Exactly one `SCHEDULED_LOCK` event; actor is `System` | Passed on both |
| Disable cleanup | Service and listener cleanup; clean shutdown | Passed on both |

The observed dispatch threads were Paper's `Server thread` and Folia's
`Folia Region Scheduler Thread #0`, respectively. EndLock's command wrappers
route player command executors to the global scheduler as well, but no real
player command was exercised during these runs.

## 3. Contract points confirmed

- The service is available after enable and is removed on disable.
- Repeated state-setting commands do not produce duplicate state-change
  events.
- Console, undo, and scheduled changes dispatch synchronously in the global
  tick context on both tested platforms.
- The service reflects runtime state changes, and `getLockReason()` returns
  the plain-text `Maintenance` fallback.
- No Folia scheduler exception or thread assertion occurred in these runs.

The event reports a runtime transition, not successful completion of every
side effect. EndLock dispatches it even if a later side effect throws. That
failure behavior is implemented but has not been tested with an injected
runtime failure.

## 4. Not verified

These scenarios need a live player session and were not part of this test:

- Portal travel or teleport into a locked End, including player-triggered
  command paths on Folia.
- Respawn when the End is the death world.
- Manual and automatic evacuation.
- Join notifications and grace periods.

The consumer's startup without EndLock has not been run as a separate runtime
smoke test. Its API-dependent classes are isolated so the consumer's main
plugin class does not directly reference types missing when EndLock is absent.

## 5. Method and evidence

- The tested state changes used real console commands or config schedules;
  no reflection or emulation was used.
- Console commands were dispatched through the consumer on the global region
  scheduler, the supported context for console commands on Folia.
- The scheduled test used EndLock's normal schedule path.
- The project is pinned to Folia 26.3 Build 5 ALPHA for local/CI compatibility
  checks. The live test confirms only the scenarios listed above; it does not
  establish compatibility for untested player/world paths.

Representative log lines:

```text
[EndLockApiConsumer] state-change: previousLocked=false, newLocked=true,
action=SCHEDULED_LOCK, actorName=System, actorUuid=null
[EndLock] Scheduled lock executed.
[EndLockApiConsumer] status tick: locked=true, reason=Maintenance
```

```text
[EndLockApiConsumer] state-change: previousLocked=false, newLocked=true, action=LOCK
The End is already locked!   # Guard: no state-change event
[EndLockApiConsumer] state-change: previousLocked=true, newLocked=false, action=UNLOCK
[EndLockApiConsumer] state-change: previousLocked=false, newLocked=true, action=UNDO
```
