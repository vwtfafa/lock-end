## 2. API-Paket und Inhalt

**Paket:** `org.vwtfafa.lockEnd.api`

Das Paket enthält **ausschließlich** die folgenden zwei Typen:

1. Das Interface `EndLockApi`:

   ```java
   public interface EndLockApi {
       boolean isLocked();

       String getLockReason();
   }
   ```

2. Die finale Event-Klasse `EndLockStateChangeEvent`
   (`extends org.bukkit.event.Event`, **nicht** `Cancellable`,
   nicht abbrechbar, synchron gemäß [J-EV]).

Alles Weitere – insbesondere die interne Provider-Klasse, die das Interface
implementiert – bleibt **außerhalb des API-Pakets** und ist ohne
API-Zusage (`@Internal`, nicht dokumentiert, kein Kompatibilitätsversprechen).
Eventuell nötige `static getHandlerList()`-Mechanik liegt im Event selbst,
nicht im `EndLockApi` (Anforderung an Events: [J-EV], [J-HL], [S-PEM]).

## 3. `EndLockApi`-Verträge

### 3.1 `isLocked()`

- Liefert den **aktuellen Laufzeitstatus** der End-Sperre zum Zeitpunkt des
  Aufrufs: `true`, wenn das End gesperrt ist, sonst `false`.
- **Semantik:** volatile-read. Der interne Zustand ist ein `volatile boolean`
  ([R-LOCK] `LockEnd.java`, Zeile 60), jedes erfolgreiche `changeLockState`
  schreibt ihn synchron im Tick-Kontext ([R-LOCK] Zeilen 204–230). Ein
  Aufruf sieht also entweder den Zustand vor oder nach dem letzten
  abgeschlossenen Zustandswechsel – niemals einen dazwischenliegenden Wert.
- Der Wert spiegelt die **aktive Laufzeitlogik** wider (das Feld, das auch
  `EndAccessGate` heranzieht, [R-LOCK] Zeilen 698–701), nicht etwa eine
  Konfigurationsvorgabe oder einen geplanten zukünftigen Zeitplan-/Undo-
  Zustand.
- **Thread-Sicherheit:** lock-free; von jedem Thread aufrufbar. Für eine
  sinnvolle Weiterverarbeitung (Welt-/Spielermutationen) gelten trotzdem die
  Scheduler-Regeln aus Abschnitt 5.
- **Nach Disable/Re-Enable:** Während EndLock deaktiviert ist, existiert
  kein Service (Abschnitt 6); `isLocked()` ist dann schlicht nicht erreichbar.

### 3.2 `getLockReason()`

**Plain-Text-Kontrakt** (Projekteinhaber-Entscheidung, fest):

- Der Rückgabewert ist **Plain Text**: keine MiniMessage-Tags (`<...>`),
  keine Legacy-`§`-Farbcodes. Der interne Provider muss die Bereinigung
  implementieren und dokumentieren: Formatierungscodes (MiniMessage-Tags
  und `§`-Sequenzen) werden aus dem konfigurierten Grund **entfernt**
  (stripped), nicht in irgendeine Renderform überführt.
- Der Rückgabewert ist **niemals `null`**.
- **Regel ohne gesetzten/leeren Grund:** Der Rückgabewert ist der
  **effektive Grund, den EndLock den Spielern anzeigt**: Fällt der
  konfigurierte Wert fort, gilt derselbe eingebaute Fallback wie in der
  Spieler-Nachricht (`"Maintenance"` aus `LockReasonManager`, Zeilen 12 und
  28). Bleibt ein gesetzter Grund nach der Bereinigung leer, gibt
  `getLockReason()` den **leeren String** (`""`) zurück.
  Begründung: Ein Verbraucher, der die API fragt, soll exakt die Information
  bekommen, die ein zeitgleich blockierter Spieler in seiner Meldung sehen
  würde; eine Sonderregel „leer, wenn nicht gesetzt“ würde vom
  Bestandsverhalten abweichen und die Dokumentation aufwendig machen.
- **Quelle des Werts:** der effektiv anzuwendende default-Grund; gelesen über
  `LockReasonManager.getReason("default")` ([R-LOCK] `LockEnd.java` Zeilen
  424–426; `LockReasonManager.java` Zeilen 27–28, 36–42), danach
  Plain-Text-Bereinigung des zurückgegebenen Wertes.

- **Thread-Sicherheit:** Der Wert kommt aus einer unveränderlichen Map
  (`Map.copyOf`, `LockReasonManager.java` Zeile 26) hinter einem
  `volatile`-Feld (`LockEnd.java` Zeile 82); der zurückgegebene `String`
  ist unveränderlich. Ein Aufruf aus jedem Thread ist daher wohldefiniert;
  Geschäftslogik-Konsistenz („Reason passt zu Status“) garantiert der
  Vertrag nicht – Status und Reason können zwischen zwei Aufrufen
  unabhängig wechseln.
- Der konfigurierte Grund darf Unicode enthalten (R4 aus der
  Machbarkeitsrecherche, Abschnitt 8); der Vertrag stellt keine
  Zeichensatz-Einschränkung, nur die Plain-Text-Regel.
  [Aufgelöst 31.10.2026, Projekteinhaber:Plain-Text-Kontrakt; Fallback wie
  oben = effektiver Grund inklusive interner Fallback-Regel.

**Aufgelöster Abstimmungspunkt mit dem Bestandscode:** Der aktuelle
`LockReasonManager` fällt bei fehlendem `lock-reasons.default`-Eintrag
intern auf `"Maintenance"` zurück (`LockReasonManager.java` Zeile 12, 28).
Der Vertrag übernimmt dieses Bestandsverhalten (siehe oben) und definiert
keinerlei eigene Sonderregel „kein Grund“; der Provider strahlt die
Fallback-Logik ein und macht ausschließlich die Plain-Text-Bereinigung.

## 4. `EndLockStateChangeEvent`-Vertrag

### 4.1 Klasse

```java
public final class EndLockStateChangeEvent extends org.bukkit.event.Event {
    // final, nicht Cancellable
}
```

- Ein synchrones Event ([J-EV]; kein Async-Modus).
- **Nicht abbrechbar:** Das Event meldet eine bereits abgeschlossene,
  erfolgreiche Änderung; es kann sie nicht nachträglich verhindern
  (ROADMAP-§1). Kein `Cancellable`, kein `setCancelled`.
- `static getHandlerList()`-Schablone wie in der Machbarkeitsrecherche,
  Abschnitt 3.1 ([J-EV], [J-HL], [S-PEM]).

### 4.2 Felder

| Feld | Typ | Bedeutung |
|---|---|---|
| `previousLocked` | `boolean` | Sperrstatus unmittelbar vor dem Wechsel |
| `newLocked` | `boolean` | Sperrstatus nach dem Wechsel (immer ungleich `previousLocked`) |
| `action` | `String` | Auslösende Aktion; stabiler, dokumentierter Wertesatz (4.3) |
| `actorName` | `@Nullable String` | Anzeigename des Akteurs oder `"System"` beim Zeitplan |
| `actorUuid` | `@Nullable UUID` | UUID des Akteurs, falls vorhanden |

Werte-Regeln für Akteur:

- **Befehl durch Spieler/Entity-Akteur** (`lock`/`unlock`/`undo`):
  `actorName` = `actor.name()`, `actorUuid` = `actor.uuid()`
  ([R-CMD] `EndLockCommand.java` Zeilen 223, 274, 289, 365;
  `UndoCommand.java` Zeilen 29–40).
- **Konsole:** `actorName` = Konsolename, `actorUuid` = `null`
  (`UndoCommand.java` Zeilen 30–32: UUID nur bei Entity-Sender).
- **Zeitplan:** `actorName` = `"System"`, `actorUuid` = `null`
  ([R-SCHED] `ScheduleManager.java` Zeile 380 – hier existiert keine UUID).
- Die Annotationsform `@Nullable` ist Teil des öffentlichen Vertrags;
  Verbraucher müssen mit `null` rechnen, auch wenn die heutigen Aufrufer
  `actorName` faktisch nie `null` liefern.

### 4.3 `action`-Wertesatz (im Code verifiziert)

Der Wertesatz ist **im Code verifiziert**; unbekannte Werte sind laut Vertrag
nicht ausgeschlossen (Vorwärtskompatibilität), Verbraucher müssen tolerant
parsen. Die aktuellen, definitiven Werte laut Code:

| `action` | Erzeugende Stelle | Verifizierung |
|---|---|---|
| `"LOCK"` | `EndLockCommand` → `plugin.changeLockState(newLocked, actor.name(), newLocked ? "LOCK" : "UNLOCK", actor.uuid())` | `EndLockCommand.java` Zeile 223 sowie Zeile 274 (`changeLockState(true, ..., "LOCK", ...)`) |
| `"UNLOCK"` | dieselbe Aufrufstelle wie oben (ternär) sowie Zeile 289 (`changeLockState(false, ..., "UNLOCK", ...)`) | `EndLockCommand.java` Zeilen 223, 289 |
| `"UNDO"` | `undoLastAction` → `changeLockState(restored, actor, "UNDO", actorUuid)` | `LockEnd.java` Zeile 241; ausgelöst über `EndLockCommand.java` Zeile 365 → `UndoCommand.java` Zeilen 34–40 |
| `"SCHEDULED_LOCK"` | `executeDueAction` → `plugin.changeLockState(targetLocked, "System", "SCHEDULED_" + scheduledAction.toUpperCase(Locale.ROOT))` mit `scheduledAction == "lock"` | `ScheduleManager.java` Zeile 380; zulässige Werte für `scheduledAction` sind nur `lock`/`unlock` (`isSupportedAction`, `ScheduleManager.java` Zeilen 331–333) |
| `"SCHEDULED_UNLOCK"` | dieselbe Stelle mit `scheduledAction == "unlock"` | `ScheduleManager.java` Zeilen 331–333, 380 |

Damit sind die fünf Werte `LOCK`, `UNLOCK`, `UNDO`, `SCHEDULED_LOCK`,
`SCHEDULED_UNLOCK` **im Repository-Code zeilengenau verifiziert**. Die
Groß-/Kleinschreibung der `SCHEDULED_*`-Werte ergibt sich deterministisch
aus `"SCHEDULED_" + "lock".toUpperCase(Locale.ROOT)` bzw.
`"SCHEDULED_" + "unlock".toUpperCase(Locale.ROOT)`.
Andere `action`-Strings (`"TEST"` für `logTestAction`, `LockEnd.java`
Zeilen 453–455) führen **kein** Zustandswechsel-Event, weil sie kein
`changeLockState` aufrufen.

### 4.4 Auslösungsregeln

- **Ausgelöst GENAU EINMAL** je **erfolgreichem** Zustandswechsel durch die
  interne Methode `changeLockState` ([R-LOCK] Zeilen 204–230).
- **Nicht ausgelöst**, wenn der gewünschte Zustand bereits aktiv ist: der
  Guard `if (locked == newLocked) return false;` ([R-LOCK] Zeilen 205–207)
  kehrt ab, bevor ein Event gefeuert würde.
- **Nicht ausgelöst**, wenn die Änderung fehlschlägt. Der genaue
  Feuerrpunkt innerhalb `changeLockState` (vor oder nach Persistenz- und
  Broadcast-Zweig) und das Verhalten bei `config.save`-/Broadcast-Fehlern
  sind im Prototyp zu prüfen (Risiko R6 der Machbarkeitsrecherche).
- **Nicht ausgelöst:**
  - beim Serverstart beim Wiederherstellen des persistierten Zustands (in
    `onEnable` läuft kein `changeLockState`, [R-LOCK] Zeilen 146–150),
  - bei geplanten (`lockat`/`unlockat`/`lockin`/`unlockin`) und Countdown-
    Anläufen, solange sie nur eine ausstehende Aktion registrieren
    ([R-SCHED] Zeilen 400 ff.),
  - bei `/endlock undo`, wenn `getLastPreviousState() == null`
    ([R-LOCK] Zeilen 236–246: `undoLastAction` kehrt ohne
    `changeLockState` ab),
  - beim `TEST`-Logging (`logTestAction`) und bei rein lesenden
    Gate-Events (Teleport/Respawn),
    die den Zustand nur **lesen**, nicht ändern.
- **Reihenfolge:** Die Nebenwirkungen des Zustandswechsels (Statistik,
  Persistenz, Broadcast, Verlauf, Log über `recordStateChange`,
  `getConfig().set`/`saveConfig`, `broadcastLockState`, `logAction` und
  `historyCommand.addEntry`,
  ([R-LOCK] Zeilen 211–224) laufen im selben
  `changeLockState`-Durchlauf; die exakte Einordnung des Events
  (vor/nach Broadcast) ist Implementierungspunkt und im Prototyp
  festzulegen (R6).

## 5. Ausführungskontext (Thread-Vertrag)

Basiert auf der Machbarkeitsrecherche, Abschnitte 4 und 5.

### 5.1 Dispatch-Kontext

Das Event ist **synchron** und wird im **Aufruferkontext** der auslösenden
Aktion gefeuert:

| Auslöser | Paper 26.3 | Folia 26.3 |
|---|---|---|
| Command durch Spieler/Entity-Akteur | main thread | Tick-Kontext der Region, die den Akteur besitzt ([F-README], [F-PPATCH]) |
| Konsole | main thread | Global-Region-Thread ([F-README], [F-PPATCH]) |
| `/endlock undo` | main thread | wie Command |
| Zeitplan (fällige Aktion) | main thread | Global-Region-Thread, weil `executeDueAction` innerhalb der `runGlobalLater`-Task läuft ([R-SCHED] Zeilen 371–380, [J-GRS]) |
| AsyncScheduler / Plugin-Worker | **nie** (IllegalStateException, [S-PEM]) | **nie** |

Es gibt im aktuellen Codestand **keinen asynchronen `changeLockState`-
Aufrufer** (Repositorianalyse [R-LOCK], [R-CMD], [R-SCHED] in
Machbarkeitsrecherche Abschnitt 5). Der Dispatch von einem Nicht-Tick-Thread
aus würde auf beiden Plattformen eine `IllegalStateException` auslösen
([S-PEM], „may only be triggered synchronously“); auf Folia gelten
Regionen- und Global-Region-Threads als synchron ([F-README]).

### 5.2 Vertrag statt Thread-Garantie

Der Vertrag sagt bewusst **nicht** „Thread X garantiert“, sondern:
**„synchrones Event im Tick-Kontext der auslösenden Aktion +
Listener-Scheduler-Regeln“** (Risiko R3 der Machbarkeitsrecherche;
Folia-„Super aggressive thread checks“ sind offiziell geplant [F-README]).
Damit bleibt der Vertrag stabil, wenn Folia künftige Thread-Prüfungen
verschärft.

### 5.3 Listener-Regeln

1. **Payload nur lesen.** Ein Handler darf `previousLocked`, `newLocked`,
   `action`, `actorName`, `actorUuid` konsumieren.
2. **Keine direkten Welt-/Spieler-Mutationen im Handler.** Auf Folia
   insbesondere keine Teleporte, Block-/Entity-Änderungen, Scoreboards oder
   Portale direkt im Handler; dafür RegionScheduler / EntityScheduler /
   GlobalRegionScheduler verwenden ([F-README], [J-GRS]).
3. Handler laufen synchron im Dispatch-Thread; ein fehlerhafter
   Listener bricht die Änderung nicht (er wird geloggt, in
   `ServerExceptionEvent` verpackt; [S-PEM]); aber er kann auch nicht
   „revertieren“.
4. Listener deaktivierter Plugins werden beim Dispatch übersprungen
   ([S-PEM]); Verbraucher müssen 6. (Lebenszyklus) beachten.

## 6. Lebenszyklus der Service-Registrierung

- **Registrierung in `onEnable`, NACH** dem Aufbau der internen
  Zustandsobjekte: das schließt die Initialisierung des `volatile boolean
  locked` (config-geladen, `LockEnd.java` Zeilen 107) und des
  `volatile LockReasonManager lockReasonManager` (`LockEnd.java` Zeilen
  82, 116) **ein**; der Provider darf erst registriert werden, wenn
  `isLocked()` und `getLockReason()` sinnvoll bedientbar sind. Orientierungs-
  punkt in `onEnable`: nach Zeile 116 (bzw. nach `refreshCachedConfig()`,
  falls weitere volatile Caches einbezogen werden).
- Registrierungsaufruf (gemäß Machbarkeitsrecherche, Abschnitt 2.1/6.1):
  `getServer().getServicesManager().register(EndLockApi.class, provider,
  this, ServicePriority.Normal)` ([J-SM]).
- **Auto-Unregister beim Disable:** serverseitig garantiert
  (`unregisterAll(plugin)` im Disable-Pfad, [S-PPIM]; die Folia-Übernahme
  ist quellcode-plausibel, nicht live geprüft, R1).
- **Verbraucher MÜSSEN:**
  - den Provider **nicht cachen**; der Service wird bei jedem
    Disable/Enable-Zyklus entfernt und neu registriert (R5). Stattdessen
    dynamisch pro Nutzung `getRegistration(...)`/`load(...)` anfragen
    ([J-SM], Machbarkeitsrecherche 2.4).
  - **Event-Listener nach einem Re-Enable von EndLock neu registrieren**;
    Event-Handler werden ebenfalls im Disable-Pfad abgemeldet
    ([S-PPIM] `HandlerList.unregisterAll(plugin)`).
  - Ein fehlender Service (EndLock fehlt oder ist deaktiviert) ist ein
    normaler Zustand, kein Fehler (ROADMAP-§1).
- **Reload/Re-Enable-Verhalten:** Nach `/reload` oder Re-Enable von EndLock
  existiert ein neuer Provider; alte Referenzen sind ungültig (R5).
  Szenarien „EndLock reload, Verbraucher bleibt“ sind im Prototyp
  zu dokumentieren (Abschnitt 9, Prototyp-Tests).

## 7. Verteilung & Abhängigkeit (Projekteinhaber-Entscheidung, fest)

1. **Verteilung im ersten Schritt über das veröffentlichte Release-Jar**
   (GitHub Releases bzw. Modrinth-Distribution von EndLock 3.1), das als
   **`compileOnly`-Abhängigkeit** in Verbraucherprojekten eingebunden wird.
2. **Keine Maven-Veröffentlichung, kein JitPack** in 3.1. Keine neuen
   Repository- oder Gradle-Plugin-Mechanismen; auch das ist die
   ROADMAP-§2-Vorgabe („Für den ersten Schritt keine Maven-Veröffentlichung
   oder neue Laufzeitabhängigkeit voraussetzen“).
3. **Plugin-Metadaten der Verbraucher:** In `plugin.yml` des Verbrauchers
   ein **optionaler Laufzeitverweis**:

   ```yaml
   softdepend: [EndLock]
   ```

   `softdepend` stellt die Ladeordnung (EndLock zuerst) sicher, ohne eine
   harte Abhängigkeit zu erzwingen; `loadbefore`/`depend` sind für 3.1
   nicht vorgesehen. `api-version`, Java- und Paper-Versionen des
   Verbrauchers folgen der üblichen Verbraucher-Praxis, nicht diesem
   Vertrag.

4. Das Release-Jar enthält das API-Paket (Abschnitt 2). Die
   compileOnly-Kompilierung bindet es nur zur Typauflösung ein; zur
   Laufzeit bietet EndLock selbst die Provider-Instanz über den
   ServicesManager an (kein shaden des API-Pakets im Verbraucher).

## 8. Beispiel-Consumer-Snippet (SKELETON)

> **Achtung: SKELETON, kein verifizierter Produktionscode.** Das
> vollständige, versionsgeprüfte Beispiel kommt mit der Implementierung
> per ROADMAP „Empfohlene Reihenfolge“ Schritt 4. Es kompiliert gegen das
> Release-Jar der 3.1-API; die genannten Klassen existieren erst nach der
> Implementierung.

```java
public final class ExampleConsumer extends JavaPlugin implements Listener {

    @Override
    public void onEnable() {
        // optionaler Laufzeitverweis
        if (getServer().getPluginManager().getPlugin("EndLock") != null) {
            getServer().getPluginManager().registerEvents(this, this);
        }
    }

    private EndLockApi api() {
        // NICHT cachen – dynamisch pro Nutzung anfragen (Abschnitt 6)
        RegisteredServiceProvider<EndLockApi> reg =
                Bukkit.getServicesManager().getRegistration(EndLockApi.class);
        return reg == null ? null : reg.getProvider();
    }

    private void checkStatus() {
        EndLockApi api = api();
        if (api == null) {
            // EndLock fehlt oder ist deaktiviert: normal weiterlaufen
            return;
        }
        boolean locked = api.isLocked();
        String reason = api.getLockReason(); // Plain Text, kein Markup
        // ... eigene Anzeige/Meldung des Verbrauchers
    }

    @EventHandler
    public void onLockStateChange(EndLockStateChangeEvent event) {
        // Payload nur lesen; Welt-/Spieler-Mutation nur über
        // RegionScheduler/EntityScheduler/GlobalRegionScheduler
        if (!event.newLocked()) {
            // z. B. eigenes Event-Plugin starten; World-/Spieler-Aktionen
            // ueber RegionScheduler/EntityScheduler schedulen
        }
    }
}
```

Die Accessor-Namensform (`event.newLocked()` vs. `getNewLocked()`) ist im
Skeleton nicht final; die Implementierung wählt dieselbe Konvention wie im
umliegenden Event-Code und dokumentiert sie. Geprüft im Prototyp werden
außerdem Folia-Dispatch-Kontexte (Prototyp-Tests Machbarkeitsrecherche §9).

## 10. Versionsregeln

- Die API-Version gleich der EndLock-Feature-Version: 3.1 liefert die API
  „3.1“.
- **Kompatible Änderungen** innerhalb von 3.x: neue, zukünftig mögliche
  `action`-Werte (tolerant parsen, Abschnitt 4.3), neue nullable Details,
  nicht entfernte Felder. Verbraucher dürfen nicht davon ausgehen, dass
  der `action`-Wertesatz abgeschlossen bleibt.
- **Inkompatible Änderungen** (Signaturen, Felder, Paket) erfordern ein

## 11. Zusammenfassung

- **API-Paket `org.vwtfafa.lockEnd.api`** mit exakt `EndLockApi`
  (`isLocked()`, `getLockReason()`) und `EndLockStateChangeEvent`
  (finale Klasse, `extends Event`, nicht `Cancellable`).
- **`getLockReason()`** liefert Plain Text ohne MiniMessage-Tags und ohne
  `§`-Sequenzen; niemals `null`; ohne gesetzten/leeren Grund `""`
  (Abstimmungspunkt mit dem internen `Maintenance`-Fallback, Abschnitt 3.2).
- **Event** feuert GENAU EINMAL je erfolgreichem Zustandswechsel aus
  `changeLockState`; nicht bei getroffenem Guard (bereits aktiver
  Zielzustand) und nicht bei fehlgeschlagener Änderung. Felder:
  `previousLocked`, `newLocked`, `action`, `actorName`, `actorUuid`.
- **action-Werte (im Code zeilengenau verifiziert):** `"LOCK"`
  (`EndLockCommand.java:223, 274`), `"UNLOCK"` (`EndLockCommand.java:223, 289`),
  `"UNDO"` (`LockEnd.java:241`), `"SCHEDULED_LOCK"` /
  `"SCHEDULED_UNLOCK"` (`ScheduleManager.java:380`, begrenzt auf
  `lock`/`unlock` durch `isSupportedAction`, `ScheduleManager.java:331–333`).
- **Thread-Vertrag:** synchrones Event im Tick-Kontext der auslösenden
  Aktion (Paper: main thread; Folia: Spielerregion bzw. Global-Region);
  nie AsyncScheduler; Listener mutieren Welt/Spieler nur über Scheduler.
- **Lebenszyklus:** Registrierung in `onEnable` nach Aufbau
  `locked`/`lockReasonManager`; Auto-Unregister beim Disable;
  Verbraucher cache-frei: Provider dynamisch anfragen, Listener nach
  Re-Enable neu registrieren.
- **Verteilung:** Release-Jar (GitHub Releases/Modrinth) als
  `compileOnly`; `softdepend: [EndLock]`; keine Maven-/JitPack-
  Veröffentlichung in 3.1.
- **Offen vor Prototyp:** R6 (Feuerrpunkt bei Persistenz-/Broadcast-Errors),
  R1 (Folia-live-Beleg). `getLockReason()` (R4-Nachfolge) ist aufgelöst
  (Abschnitt 3.2).
