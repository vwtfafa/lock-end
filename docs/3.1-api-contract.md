# EndLock 3.1 – Public API Contract

> **Status:** Contract for the implemented read-only API in EndLock 3.1.
> The API and consumer prototype are present in this repository. Console and
> scheduled paths were live-tested on Paper and Folia. Player-driven paths
> have not been live-tested, and EndLock hot-reload is not supported.
>
> Last verified: 2026-11-01.

## 1. Scope and compatibility

The supported public surface consists of two types in
`org.vwtfafa.lockEnd.api`:

1. `EndLockApi`, a read-only service interface.
2. `EndLockStateChangeEvent`, a synchronous, non-cancellable event.

Implementation classes, provider objects, managers, configuration structures,
and mutable internal collections are not public API. The API does not expose
methods to lock or unlock the End. All state changes continue through
EndLock's existing commands and runtime logic.

## 2. Public types

### `EndLockApi`

```java
public interface EndLockApi {
    boolean isLocked();

    String getLockReason();
}
```

#### `isLocked()`

- Returns the current runtime state, not a configured or scheduled future
  state.
- The implementation reads a `volatile` state field, so calls are
  thread-safe and lock-free.
- The state may change between separate calls. The API does not promise an
  atomic snapshot of state and reason together.
- The service is unavailable while EndLock is disabled.

#### `getLockReason()`

- Returns plain text and never `null`.
- Recognized MiniMessage tags and valid legacy `§` formatting codes are
  stripped. They are not rendered.
- Ordinary angle-bracket text such as `Portal <The End>` is preserved.
- Unicode is allowed.
- If `lock-reasons.default` is missing, the existing provider fallback
  `"Maintenance"` is returned.
- An explicitly empty value, or a value that becomes empty after formatting
  codes are stripped, returns `""`.
- Treat the value as display text, not structured data.

The reason is read from the effective default reason. State and reason may
change independently between calls.

### `EndLockStateChangeEvent`

```java
public final class EndLockStateChangeEvent extends Event {
    // Not Cancellable
}
```

The event reports a runtime transition that has already occurred. A listener
cannot cancel or reverse it. It is synchronous and is dispatched after the
runtime state field changes.

| Accessor | Type | Meaning |
|---|---|---|
| `previousLocked()` | `boolean` | State immediately before the transition |
| `newLocked()` | `boolean` | State after the transition; differs from the previous value |
| `action()` | `String` | Action that caused the transition |
| `actorName()` | `@Nullable String` | Actor name, or `null` if unavailable |
| `actorUuid()` | `@Nullable UUID` | Actor UUID, or `null` for console/system actions |

Current `action()` values are:

| Value | Meaning |
|---|---|
| `LOCK` | Lock command |
| `UNLOCK` | Unlock command |
| `UNDO` | Undo command |
| `SCHEDULED_LOCK` | Scheduled lock |
| `SCHEDULED_UNLOCK` | Scheduled unlock |

The value set is open. Consumers must tolerate values introduced by future
versions. Scheduled actions currently use actor name `"System"` and a
`null` UUID. Console actions use the console sender name and a `null` UUID.
Player/entity actions use the actor's display name and UUID.

## 3. Event delivery and failure semantics

Exactly one event is dispatched for each actual runtime transition.
No event is dispatched when:

- The requested state is already active.
- Startup restores persisted state.
- A future schedule is registered but has not executed.
- An undo operation has no previous state to restore.
- A read-only path observes or rejects an action without changing state.

The runtime state is assigned before side effects such as persistence,
broadcast, history, grace-period handling, or evacuation scheduling. If a
subsequent side effect throws, EndLock still attempts to dispatch the event
and rethrows the original failure. If event dispatch also throws, that event
failure is attached as a suppressed exception; it does not replace the
original side-effect failure. If there was no side-effect failure, an event
dispatch failure propagates normally.

Therefore, the event confirms a runtime state transition; it does not
guarantee that persistence or every side effect completed successfully.

## 4. Threading

Event handlers run synchronously in the dispatch context:

| Platform/path | Dispatch context |
|---|---|
| Paper 26.3 | Server main tick thread |
| Folia 26.3 | Global-region tick thread |

EndLock routes its command executors, including player-command executors,
through its global scheduler. Scheduled state changes already run there.
Console and scheduled paths were live-tested on Paper 26.3 and Folia 26.3
Build 5 ALPHA. Player-driven Folia paths were not tested with a live player.

Do not depend on thread names. The event handler should consume the event
payload only. It must not assume it owns an arbitrary player or region.
Schedule world, block, and entity changes through the appropriate Paper/Folia
global, region, or entity scheduler. Do not fire this synchronous event from
an asynchronous or plugin-worker thread.

## 5. Service lifecycle

EndLock registers the service during enable, after the runtime state and
reason provider are initialized:

```java
getServer().getServicesManager().register(
        EndLockApi.class, provider, this, ServicePriority.Normal);
```

Paper removes services registered under the owning plugin when that plugin is
disabled. Consumers should:

- Look up the service through `ServicesManager` when needed.
- Treat a missing service as a normal optional-dependency state.
- Avoid caching the provider; it is removed on disable.

Hot-enabling or hot-reloading EndLock while a consumer remains enabled is not
supported. After installing, updating, or reloading EndLock, restart the
server. Consumers that must run without EndLock must isolate all references
to API types in a separate integration class and load that class only when
EndLock is enabled. `softdepend` establishes load order but does not supply
classes when EndLock is absent.

## 6. Distribution and consumer dependency

For 3.1, the API is distributed in the EndLock release JAR. There is no
separate Maven publication or JitPack dependency. Consumer projects should
use the release JAR as `compileOnly`, must not shade API classes, and should
declare:

```yaml
softdepend: [EndLock]
```

The standalone example is in [`examples/api-consumer`](../examples/api-consumer).
See the [integration guide](3.1-integration-guide.md) for a working setup.

## 7. Compatibility policy

- The two types above are the complete supported API surface for 3.1.
- Provider classes and implementation details may change without API
  compatibility guarantees.
- Incompatible changes to public types require an API-version change.
- New `action()` values may be added compatibly; consumers must allow unknown
  values.
- The API remains read-only. Adding mutation methods or unrelated data requires
  a separately justified API design.

## 8. Verification status

Service registration/removal, console changes, undo, scheduled actions, and
global synchronous event dispatch were verified with the consumer prototype
on Paper 26.3 and Folia 26.3 Build 5 ALPHA. No injected side-effect failure
has been used to exercise the partial-failure path. Player travel, respawn,
evacuation, join/grace-period behavior, and player commands on Folia remain
outside the live verification scope.
