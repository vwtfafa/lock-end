# EndLock 3.1 API – Integration Guide

This guide is for plugin developers who want to read EndLock's lock state or
observe changes. The API is read-only. The detailed contract is in
[3.1-api-contract.md](3.1-api-contract.md); verification results are in
[3.1-prototype-verification.md](3.1-prototype-verification.md).

## 1. API overview

EndLock 3.1 provides two public types in `org.vwtfafa.lockEnd.api`:

| Type | Purpose |
|---|---|
| `EndLockApi` | Query the current runtime state with `isLocked()` and the effective plain-text reason with `getLockReason()`. It is registered as a Bukkit service. |
| `EndLockStateChangeEvent` | Observe a completed runtime state transition. The event is synchronous and not cancellable. |

Consumers can display EndLock's status, react when the End opens, or integrate
without reading EndLock's configuration. They cannot change the lock through
this API. Existing EndLock commands, schedules, history, broadcasts, grace
periods, and evacuation remain the state-changing paths.

## 2. Add the compile-time dependency

The API is included in the EndLock release JAR. There is no Maven publication
in 3.1; use the release JAR as a `compileOnly` dependency:

```kotlin
repositories {
    mavenCentral()
    maven { url = uri("https://repo.papermc.io/repository/maven-public/") }
}

dependencies {
    compileOnly("io.papermc.paper:paper-api:26.3.build.209-stable")
    compileOnly(files("libs/lock-end-3.1.0.jar"))
}
```

Do not shade EndLock's API classes into the consumer. EndLock supplies the
service at runtime.

Declare EndLock as an optional dependency to establish load order when it is
installed:

```yaml
softdepend: [EndLock]
```

### Optional class-loading

Because `compileOnly` classes are absent when EndLock is not installed, keep
all references to `EndLockApi` and `EndLockStateChangeEvent` in a separate
integration class. Load that class only when EndLock is enabled:

```java
@Override
public void onEnable() {
    if (getServer().getPluginManager().isPluginEnabled("EndLock")) {
        new EndLockIntegration(this).enable();
    }
}
```

Do not put API-typed fields, listener methods, or class literals in the
consumer's main plugin class if that plugin must also start without EndLock.
`softdepend` provides load order, but cannot provide classes when EndLock is
absent.

Hot-enabling or hot-reloading EndLock while the consumer remains enabled is
not supported. Restart the server after installing, updating, or reloading
EndLock.

## 3. Find the service

Query the `ServicesManager` when the API is needed:

```java
RegisteredServiceProvider<EndLockApi> registration =
        getServer().getServicesManager().getRegistration(EndLockApi.class);
EndLockApi api = registration == null ? null : registration.getProvider();
```

- A missing registration means EndLock is absent or disabled. Treat this as a
  normal optional-integration state.
- Do not cache the provider. EndLock removes it when disabled; request it
  again when needed.
- The service is registered at `ServicePriority.Normal`.

## 4. Lock reason

`getLockReason()` returns plain text and never returns `null`.

- Supported MiniMessage tags and valid legacy `§` formatting codes are
  stripped, not rendered.
- Ordinary text in angle brackets, such as `Portal <The End>`, and Unicode
  characters are preserved.
- If `lock-reasons.default` is missing, the internal `"Maintenance"` fallback
  is returned.
- An explicitly empty value, or a value that becomes empty after stripping,
  returns `""`.

Treat the reason as display text, not structured data.

## 5. Observe state changes

Register a listener from the isolated integration class:

```java
public final class LockStateLogger implements Listener {
    private final JavaPlugin plugin;

    public LockStateLogger(JavaPlugin plugin) {
        this.plugin = plugin;
    }

    @EventHandler
    public void onStateChange(EndLockStateChangeEvent event) {
        plugin.getLogger().info("End "
                + (event.newLocked() ? "locked" : "unlocked")
                + " by " + event.action());
    }
}
```

The event fires exactly once after each actual runtime state transition. It
does not fire when the target state is already active, when the persisted
state is restored at startup, when a future schedule is merely registered,
when undo has no previous state, or on read-only paths such as blocked travel
attempts.

The runtime state is assigned before side effects. If a later side effect
throws, EndLock still attempts to dispatch the event and rethrows the original
failure. If event dispatch also fails, that exception is suppressed onto the
original failure. The event reports the runtime transition; it does not
promise that persistence and every side effect succeeded.

Event fields:

| Accessor | Type | Meaning |
|---|---|---|
| `previousLocked()` | `boolean` | State immediately before the transition |
| `newLocked()` | `boolean` | State after the transition |
| `action()` | `String` | Current values: `LOCK`, `UNLOCK`, `UNDO`, `SCHEDULED_LOCK`, `SCHEDULED_UNLOCK`; the set is open |
| `actorName()` | `@Nullable String` | Sender name, `"System"` for scheduled actions; may be `null` |
| `actorUuid()` | `@Nullable UUID` | Entity UUID; `null` for console and scheduled actions |

Tolerate unknown future `action()` values.

## 6. Threading and Folia

The event is synchronous and is dispatched on EndLock's global tick context.
EndLock routes its state-changing command executors through the global
scheduler; scheduled actions already run there.

| Trigger | Paper 26.3 | Folia 26.3 |
|---|---|---|
| Player/entity command | Main thread | Global region thread after EndLock's command wrapper |
| Console command | Main thread | Global region thread |
| Scheduled action | Main thread | Global region thread |

Do not depend on thread names. The event handler should read its payload only.
For world or player changes, use the appropriate region, entity, or global
region scheduler; do not assume the event context owns an arbitrary entity or
region.

## 7. Compatibility and verification

The public surface is limited to the two API types above. Provider classes and
configuration internals are not supported API. Incompatible public changes
require an API-version change; new `action()` values may be added compatibly.

The service, console, undo, and scheduled paths were live-tested on Paper 26.3
and Folia 26.3 Build 5 (ALPHA). Player-driven Folia paths still require
verification with a live player. See the
[verification report](3.1-prototype-verification.md) for precise limits.
